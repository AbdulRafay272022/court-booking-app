# Decisions made without asking (audit build, 2026-10-28)

The brief said: when something is unclear, pick the safest option, write it here, continue. Each line: what, why, how to change it.

| # | Item | Decision | Why |
|---|---|---|---|
| 1 | P1.2 venue visibility | A pending/rejected/deleted venue's PUBLIC page (web server render has no login) is now a 404 even for its owner; the owner still sees it in the dashboard, status screen and walk-ins (those calls carry the token). | Never leak a hidden venue; the owner has every other surface. |
| 2 | P1.4 booking detail | The detail view is the existing `/booking/{id}/done` page (web) and status screen (app), extended, not a new route. Every card opens it for every status; held bookings still have the "pay" button there. | One detail page per platform, no duplicate screens. |
| 3 | P1.4 timeline | The player's timeline never shows staff names (who at the venue approved / marked what). | Venue-internal information. |
| 4 | P1.6 photos | Public venue REVIEWS keep showing only the first name and an initial, no photo; chat bubbles stay without avatars (Floodlight design). The photo is shown in the web header + profile menu, account hub, app home header + profile tab + owner "More", owner/staff booking rows, overview table, booking detail (web + app) and approvals (web + app). | Reviews are public: a face next to a first name is a privacy step the founder did not ask for. |
| 5 | P1.10 refund for a cancelled payment_submitted booking | NOT created automatically. The existing owner step stays the correct entry: the greyed card on Approvals has "Paisa aa gaya - Refund banayein", which creates the refund row for the screenshot amount once the owner sees the money in the bank. | An automatic row would put money that may never have arrived on the Refunds list. |
| 6 | P1.10 cash-paid booking cancelled | Needs `payment_disputes.payment_id` nullable (a cash booking has no payment row). Done in Phase 2 item 3 (migration). Phase 1 only stops the false "refund owed" notice. | Brief: schema changes go to Phase 2. |
| 7 | P1.12 Roman Urdu | Translated the owner dashboard words the audit flagged (nav, KPI labels, statuses, buttons, check-in copy, payment-check sentences via a new `text_ru` from the backend). Kept as is on purpose: loanwords Pakistanis use as they are (Booking, Court, Player, Slot, Total, Advance, Refund, Check-in, Staff, Premium, Reviews), the admin console (English-only by design), and the Terms/Privacy bodies (legal text, needs a lawyer before translating). | Audit B6/B7/B8/B25/B29. |
| 8 | P1.15 required settings | Timers (hold, reminders, auto-cancel) are the settings that ran on a hidden NULL default: they now start as real values, an emptied box is red and blocks Save / Send for review. Not forced: the cancellation cutoff (an empty cutoff is the explicit "any time before the start" choice next to the Allowed / Not allowed chips) and the court advance rule (empty = the per-court advance % field, which IS a required, visible value). The "Default ..." lines are gone everywhere (the component is a no-op). | Forcing a number where "no limit" is a real answer would make owners type fake values. |
| 9 | P1.15 existing venues | Live venues get a yellow banner on Venue Settings (web + app) listing the settings still on a hidden default (`unconfirmed_settings` from the API); saving the card confirms them. Nothing is blocked. | Brief: banner, do not block. |
| 10 | P1.20 Raast QR format | The QR is an EMVCo merchant-presented payload (dynamic, PKR 586, amount, account title, city, booking code as reference, CRC16) with the IBAN in tag 26 under the identifier `PK.RAAST`. That identifier and sub-tag are an ASSUMPTION: SBP's Raast QR spec is the authority. Flag `iban_qr` stays OFF until a generated code scans in Meezan, HBL, Easypaisa and JazzCash (docs/device-test-checklist.md). If one does not recognise it, only `RAAST_GUID` / the sub-tags in app/services/raast_qr.py should need to change. | No spec document in the repo; better a clearly-marked, flag-gated guess than no QR. |
| 11 | P1.20 IBAN check | The QR is only built for an IBAN that passes the ISO mod-97 checksum (the venue form still only checks the shape; a wrong IBAN gets `qr_unavailable_reason = invalid_iban` instead of a bad QR). | A QR that sends money to a mistyped account is worse than none. |
| 12 | P3.2 balance proof | A balance screenshot is never auto-approved (the owner always looks), and its "name" check is shown as "not checked" (a friend often pays the balance); the receiver account is still checked. The time window is the hold until 3 h after the slot ends. A screenshot that repeats one already sent for THIS booking counts as a duplicate. | Brief + money safety. |
| 13 | P3.2 "bank se mila lein" | Built as a screen (owner + staff with view_ledger, web + app) listing one Pakistan day's transfers, not as a daily push. | A daily push for a list that is often empty is noise; the screen is always there. Easy to add a morning push later. |
| 14 | P3.3 points discount | The discount lowers the booking PRICE (the owner funds it) and is audited (`booking.points_redeemed`); it is never recorded as money received. Usable once per booking, before the start, only if the venue switched it on; points come back if that booking is later cancelled. "Fully paid by transfer" = every positive ledger entry is a bank transfer proof (a cash or "other" entry = 0 points). Points for a booking are given once (unique per booking + reason). | Money totals must stay real; no double awards. |
| 15 | P3.4 short payment (changed 2026-10-31, founder) | +5/-20 need only `short_payment_reply` (not `player_points`). At 24 h with no reply: -20 (only what the player has, never below 0) and a message, as before. **A reply is still taken any time after that** until the due is settled (paid / waived); the +5 is given only when the reply comes within **4 days of the short-payment notice** (`ShortPaymentClaim.created_at`), once per booking (unique per booking + reason). "Ghalat hai" at any time goes to the owner as a dispute. A reply on an already settled due is refused (`REPLY_WINDOW_CLOSED`, "already settled"): there is nothing left to dispute. "Waive" (the owner decides for the player) lowers the price to what was paid (audited `booking.due_waived`) and gives the -20 back with a notice. | Founder's rule; never invent money. |
| 16 | P3.5 dues | A due = an unsettled short-payment claim (a completion that left money due). A no-show with money due is not a due. Shown only while `player_dues` is on. | The brief ties dues to short payments; no-show money is a separate decision. |
| 17 | P3.6 GPS + no-show reversal (changed 2026-10-31, founder) | "Pohanch gaya" is allowed from 1 h before the start to the end of the slot, one reading per booking. A venue pin within 300 m of a city centre (the wizard's fallback pins) is "pin_unreliable" and never highlights. **Taking back a no-show** (after "Main aaya tha" or by hand) always goes through one dialog: final price, amount received now (on top of what is already recorded, 0 to final - paid), cash or transfer. Cash = one cash ledger entry for that amount. Transfer = the screenshot is required and goes through the balance-proof flow (Approvals, same OCR / duplicate / receiver checks, never auto-approved); nothing is recorded until it is approved. Approving that screenshot gives the player **+10 points** once per booking (reason `noshow_transfer_ok`, audit `points.noshow_transfer_awarded`, notice), only with `player_points` on. The old one-tap "reverse" and "Haan" on a no-show are refused (`NOSHOW_REVERSAL_REQUIRED`): Haan used to record the whole price as cash. A changed price is audited (`booking.noshow_reversed`, old and new price). Money still due after a cash reversal follows the normal "kam mila" path. | Founder's rule; the full price is never assumed. |
| 18 | P3.8 templates (changed 2026-10-31, founder) | The five templates that copy something the app already shows (advance, balance, receipt, reminder, walk-in welcome) are sent on WhatsApp ONLY (no extra push) and only with `whatsapp_templates` on. **Walk-in welcome goes to every walk-in whose opt-in box was ticked, with or without an account.** A phone with no account has no `notification_log` row (that table needs a user), so the send is recorded as an audit row on the booking (`walkin.welcome_whatsapp`, sent / error). | No double notifications; marketing only with consent. |
| 19 | P3.7 AI chat | "Koi dusra venue?" is answered from code (no model call) with up to 3 other approved venues for the player's sport, free ones first. Fuzzy names use difflib (no new dependency); a tie asks one "kaun sa venue" question. | Brief; cheaper and no invented availability. |
| 20 | Dues "Done" (2026-10-31, founder) | "Done" asks cash or transfer. Cash = a new cash ledger entry dated today for the rest, due 0. Transfer = the screenshot is required and goes through the balance-proof flow; the due becomes 0 when it is approved (`sync_claim_after_payment`). The booking price never changes on "Done"; only "waive" lowers it. A call with no body (an app build from before this change) is treated as cash, as before. | Founder's rule; old app builds keep working. |
| 21 | Owner-reported transfers (2026-10-31) | A screenshot the OWNER attaches (dues "Done", no-show reversal) is a balance proof for exactly the amount the owner typed (`amount_claimed`), marked `origin` in `ocr_raw`. Approving it credits the typed amount by default (the owner can change it on the card), capped at what is due. Only one unreviewed screenshot per booking (existing index), so a second one is refused until the first is decided. | Same checks as every screenshot; no new table. |
| 22 | "Amount received" in the reversal dialog (2026-10-31) | Read as the money received NOW, on top of what is already recorded (the dialog shows "Pehle se mila"), the same meaning as "Baqi mein se kitna mila" in the completion dialog. The final price may not go below what was already paid (that would be a refund, which has its own flow). | Consistent with the existing completion dialog; no hidden refunds. |
